# 需求规格说明书

## 1. 项目概述

### 1.1 项目名称
Pixel Survivor — 像素风Roguelike类幸存者游戏

### 1.2 项目背景
本项目为毕业设计作品，旨在开发一款像素风格的Roguelike类幸存者游戏，包含完整的游戏客户端、管理后台和后端服务。游戏参考《Vampire Survivors》《Brotato》等市面热门同类游戏的核心玩法，并加入付费商城、好友系统、成就系统等社交与商业化功能。

### 1.3 项目目标
- 实现一款可玩性较高的像素风类幸存者游戏
- 构建完整的后端服务，支持用户管理、商城、好友等功能
- 提供管理员后台，方便运营人员管理游戏数据
- 采用合理的缓存策略，保证系统性能

### 1.4 数据归属原则

本项目采用**客户端资源 + 后端运行时数据**分离的设计模式：

- **游戏客户端资源**（本地数据）：角色定义、Buff定义、地图/关卡定义、成就定义、任务定义、商品详情等游戏内容数据，全部由 Godot 游戏客户端资源文件（JSON/Resource）定义，不存储在数据库中。
- **后端数据库**（运行时数据）：用户账户、货币余额、商品运营数据（价格/库存/上下架）、用户背包、用户角色状态、购买/充值记录、好友关系、成就/任务进度、游戏记录、排行榜、邮件、签到等涉及用户状态和交易的数据。

这种设计的优势：
1. 游戏内容更新只需更新客户端资源包，无需修改数据库
2. 减少数据库存储压力和查询开销
3. 离线模式下游戏内容完整可用
4. 符合市面主流手游（元气骑士、弹壳特攻队、Vampire Survivors等）的设计惯例

## 2. 用户角色

| 角色 | 说明 | 使用端 |
|------|------|--------|
| **玩家** | 游戏用户，可注册、登录、游戏、购买道具、添加好友 | Godot 游戏客户端 |
| **管理员** | 运营人员，管理商品运营数据、用户、查看数据 | Vue3 管理后台 |

## 3. 功能需求

### 3.1 用户系统

#### 3.1.1 注册
- 用户名：4-20位字母数字下划线
- 密码：6-20位，BCrypt加密存储
- 昵称：默认随机生成，可修改
- 注册成功赠送初始游戏币

#### 3.1.2 登录
- 在线登录：用户名+密码，返回JWT Token
- 离线登录：输入任意用户名即可进入，数据本地保存
- 离线模式限制：不可使用商城、好友、排行榜、邮件等联网功能
- 离线模式下游戏内容（角色、Buff、地图等）由客户端本地资源提供，可正常游玩

#### 3.1.3 用户信息
- 查看/修改昵称、头像
- 查看等级、经验值、游戏币、钻石余额
- 查看游戏统计（最高波数、总游戏时长等）

### 3.2 游戏大厅

#### 3.2.1 大厅场景
- 像素风格的室内/广场场景
- 玩家角色可在大厅中自由移动
- 多个功能性NPC分布在大厅中

#### 3.2.2 NPC交互
| NPC | 功能 | 说明 |
|-----|------|------|
| 商店老板 | 打开商城 | 浏览和购买道具 |
| 铁匠 | 角色强化 | 消耗游戏币永久提升角色属性 |
| 冒险家 | 选关进入 | 选择地图开始游戏 |
| 学者 | 成就系统 | 查看成就进度和领取奖励 |
| 邮差 | 邮件系统 | 查看和领取邮件奖励 |
| 签到板 | 每日签到 | 每日签到领取奖励 |
| 排行榜 | 排行榜 | 查看各类排行榜 |

### 3.3 核心玩法（Roguelike幸存者）

#### 3.3.1 角色系统
- 多个可选角色，各有不同基础属性和特殊技能
- **角色定义由游戏客户端资源文件 `characters.json` 管理**，包含角色名、基础属性、技能、武器类型、解锁条件等
- 角色解锁方式：默认解锁、等级解锁、钻石购买、成就解锁
- 局外永久强化：消耗游戏币提升生命/攻击/防御/移速
- **后端只存储用户的角色解锁状态和强化数据**（character_code + 强化次数）

#### 3.3.2 地图系统
- 多张不同难度的地图，采用经典右滑选关方式
- 关卡命名：1-1-关卡名称，方便后续扩展
- 目前规划3章，每章6关，每章第6关为无尽模式
- **地图定义由游戏客户端资源文件 `maps.json` 管理**，包含地图名、难度、波数、Boss间隔、解锁条件等
- **后端不存储地图定义数据**

#### 3.3.3 战斗系统
- 玩家自动攻击范围内敌人（或手动瞄准）
- 敌人从屏幕边缘生成，向玩家移动
- 击杀敌人掉落经验宝石、特殊掉落道具、有时限Buff
- 玩家受伤扣血，血量归零游戏结束
- **Buff定义由游戏客户端资源文件 `buffs.json` 管理**，包含Buff名称、效果类型、数值、稀有度、持续时间等
- Buff池设计：通用Buff池 + 武器模板专属Buff池，根据所选角色混合

#### 3.3.4 经验与升级
- 收集经验宝石累积经验值
- 经验满后升级，弹出Buff选择界面
- 从3个随机Buff中选择1个（类肉鸽）
- Buff包括：攻击力提升、攻速提升、移速提升、暴击率提升、生命恢复、范围伤害等
- Buff可叠加，最高叠加层数由稀有度决定

#### 3.3.5 Boss战
- 每隔一定波数出现Boss
- Boss拥有更高血量和特殊攻击模式
- 击败Boss获得大量经验和游戏币奖励
- 击败最终Boss即为通关

#### 3.3.6 局内道具
- 打开背包使用已购买的道具
- 道具效果：即时回血、临时攻击力提升、临时护盾、临时移速提升等
- 道具有冷却时间

#### 3.3.7 结算
- 死亡/通关后显示结算面板
- 统计：存活时间、击杀数、Boss击杀数、获得经验、获得游戏币
- 通关额外奖励
- 失败结算损失50%特殊掉落物（向下取整）
- 无尽模式无论如何都进入胜利结算

### 3.4 商城系统

#### 3.4.1 设计原则
- **商品详情**（名称、描述、图片、效果类型、效果值等）由游戏客户端资源文件 `shop_items.json` 定义
- **商品运营数据**（价格、库存、限购、上下架状态、时间限制）由后端数据库 `t_shop_item` 存储
- 客户端通过 `item_code` 关联本地资源和后端运营数据

#### 3.4.2 商品类型
| 类型 | 说明 |
|------|------|
| 角色皮肤 | 改变角色外观 |
| 消耗道具 | 局内使用的道具（回血、护盾等） |
| 礼包 | 组合商品，限时折扣 |

#### 3.4.3 货币体系
- **游戏币**：通过游戏内击杀、通关、签到、任务获得
- **钻石**：通过充值获得（付费货币），也可少量通过成就、签到获得

#### 3.4.4 购买流程
1. 客户端从后端获取商城商品列表（item_code + 运营数据）
2. 客户端根据 item_code 从本地资源获取商品详情（名称、描述、图片）
3. 玩家选择商品和支付方式（游戏币/钻石）
4. 客户端向后端发送购买请求（item_code + 数量 + 支付方式）
5. 后端校验库存、限购、余额，扣除货币，商品进入背包
6. 生成购买记录

#### 3.4.5 充值系统
- 选择充值档位（如6元=60钻石、30元=300钻石等）
- 选择支付方式（支付宝/微信）
- **毕业设计说明**：由于无法获取真实支付API，充值流程为模拟模式，直接返回支付成功并发放钻石
- 代码中预留支付宝/微信支付接口对接位置，注释说明

### 3.5 好友系统

#### 3.5.1 功能列表
- 搜索用户（用户名/ID）
- 发送好友请求（附带验证消息）
- 接受/拒绝好友请求
- 查看好友列表
- 删除好友
- 查看好友在线状态

#### 3.5.2 实现方式
- 当前版本：REST API 请求-响应模式
- 预留WebSocket升级路径（代码中有详细注释说明改造方案）

### 3.6 成就系统

#### 3.6.1 设计原则
- **成就定义**（名称、条件类型、条件值、奖励等）由游戏客户端资源文件 `achievements.json` 管理
- **后端只存储用户的成就进度和领取状态**（achievement_code + progress + 状态）

#### 3.6.2 成就类别
| 类别 | 示例 |
|------|------|
| 击杀类 | 累计击杀100/1000/10000个敌人 |
| 通关类 | 通关第1/3/5张地图 |
| 收集类 | 收集10/50/100种道具 |
| 等级类 | 达到10/20/30级 |
| 特殊类 | 不使用道具通关、满血通关等 |

#### 3.6.3 奖励
- 游戏币、钻石、稀有道具
- 特殊角色解锁

### 3.7 每日签到

- 每日可签到一次
- 连续签到奖励递增（7天一循环）
- 奖励：游戏币、钻石、道具
- 补签功能（消耗钻石）

### 3.8 每日任务

#### 3.8.1 设计原则
- **任务定义**（名称、类型、目标值、奖励等）由游戏客户端资源文件 `daily_tasks.json` 管理
- **后端只存储用户的任务进度和领取状态**（task_code + progress + 状态）

#### 3.8.2 任务机制
- 每日刷新3-5个任务
- 任务类型：进行游戏、击杀敌人、通关、使用道具等
- 完成任务获得游戏币/经验奖励
- 全部完成额外奖励

### 3.9 排行榜

| 排行榜 | 排序依据 |
|--------|----------|
| 波数排行 | 最高到达波数 |
| 击杀排行 | 单局最高击杀数 |
| 积分排行 | 综合积分 |

- 使用Redis Sorted Set实现实时排行
- 每赛季重置

### 3.10 邮件系统

- 系统邮件：公告、维护通知
- 补偿邮件：维护补偿、Bug补偿
- 奖励邮件：活动奖励、成就奖励
- 邮件可附带奖励（游戏币/钻石/道具）
- 邮件过期自动清理（默认30天）

### 3.11 离线收益

- 离线期间累积少量游戏币
- 上线后可领取
- 离线收益有上限（如最多累积24小时）

## 5. 非功能需求

### 5.1 性能需求
- API响应时间 < 200ms（缓存命中时 < 50ms）
- 支持100+并发用户
- Redis缓存命中率 > 80%

### 5.2 安全需求
- 密码BCrypt加密存储
- JWT Token认证，2小时过期
- API限流防刷
- SQL注入防护（MyBatis-Plus参数化查询）
- XSS防护
- CORS跨域配置

### 5.3 可靠性需求
- Redis缓存防穿透（布隆过滤器 + 空值缓存）
- Redis缓存防击穿（互斥锁 + 逻辑过期）
- Redis缓存防雪崩（随机TTL + 多级缓存 + 熔断降级）
- 数据库事务保证数据一致性

### 5.4 可维护性需求
- 代码规范，注释完善
- 统一异常处理和返回格式
- API文档自动生成（Knife4j）
- 日志记录完整

## 6. 接口约束

### 6.1 通信协议
- 游戏客户端 ↔ 后端：HTTP/HTTPS RESTful API
- 管理后台 ↔ 后端：HTTP/HTTPS RESTful API
- 数据格式：JSON

### 6.2 认证方式
- 游戏端：JWT Token（Header: Authorization: Bearer {token}）
- 管理端：JWT Token（Header: Authorization: Bearer {token}）
- 离线模式：无Token，部分接口不可用

### 6.3 统一返回格式
```json
{
    "code": 200,
    "message": "success",
    "data": {}
}
```

错误码：
| code | 说明 |
|------|------|
| 200 | 成功 |
| 400 | 请求参数错误 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 500 | 服务器内部错误 |
| 1001 | 用户名已存在 |
| 1002 | 用户名或密码错误 |
| 1003 | 账号已被封禁 |
| 2001 | 游戏币不足 |
| 2002 | 钻石不足 |
| 2003 | 商品已下架 |
| 2004 | 库存不足 |
| 2005 | 超出限购数量 |
| 3001 | 好友请求已发送 |
| 3002 | 已是好友 |
| 4001 | 今日已签到 |
| 4002 | 任务未完成 |
